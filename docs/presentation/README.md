## 1. 발표 목적과 중심 내용

발표 제목은 **「AI 기반 시장 스트레스 조기경보 시스템: 예측 검증과 운영 기록」**으로 제안한다.

발표의 중심은 기존 시장 스트레스 예측 시스템의 설계, OOS 검증 결과, 대시보드 활용이다. Z-score WATCH는 추가 연구를 통해 제품 채택 여부를 결정한 사례로 설명한다. 이후 실제 신호를 생성 시점에 보존하는 운영 기록 계획으로 연결한다.

발표를 마친 청중이 이해해야 할 내용은 다음과 같다.

- 모델이 예측하는 사건의 정의와 예측기간
- 현재 스트레스 측정과 미래 위험 점수의 차이
- Logistic과 XGBoost의 성능 차이가 운영 선택에 주는 의미
- WATCH 연구를 종료하고 제품에 추가하지 않은 근거
- 과거 재생 결과와 앞으로 축적할 실전 기록의 차이

청중은 AI·금융 프로젝트 평가자로 가정한다. 처음 등장하는 MSI, OOS, purge는 쉬운 표현으로 설명하고 상세 수식은 부록에 둔다.

## 2. 확정한 제품 구조와 연구 범위

| 구성 | 발표에서 설명할 역할 |
| --- | --- |
| Risk Score | 기존 XGBoost 모델이 산출하는 향후 10거래일 위험 점수. 기존 운영 경보 기준 유지 |
| MSI | 현재 시장 스트레스 수준 측정 |
| Stress Event | 관측 MSI가 프로젝트에서 정한 사건 기준을 충족한 상태 |
| D3 | WATCH의 추가 효용을 점검한 별도 실제 급락 평가 기준 |
| Z-score WATCH | 연구 종료 및 메인 제품 경보 미채택 |

Stress Event와 D3는 정의가 다르다. 기존 모델의 학습 타깃을 D3로 바꾼 것처럼 설명하지 않는다. 기존 XGBoost의 `WATCH` 점수 구간과 별도 `Z-score WATCH` 연구 신호도 구분한다.

종료한 것은 별도 Z-score WATCH 경보 연구다. MSI의 rolling Z-score 표준화와 기존 모델 입력변수의 Z-score 사용은 유지한다. 이번 발표를 위해 모델·타깃을 변경하거나 새 튜닝을 진행하지 않는다.

## 4. 슬라이드별 핵심 내용과 발언 초안

### 1장. 연구 질문과 활용 목적

**화면:** 대시보드 대표 화면, 연구 질문 한 문장.

**발언 초안**

현재 관측 가능한 시장정보를 이용해 향후 10거래일 안에 시장 스트레스 사건이 나타날 위험을 평가했습니다. 사용자가 위험 수준과 주요 원인을 확인하고, 관련 익스포저나 스트레스 시나리오를 추가 점검하도록 돕는 것이 목적입니다.

익스포저 점검은 활용 시나리오다. 실제 포트폴리오 분석 기능을 구현했다는 의미로 제시하지 않는다.

### 2장. 데이터와 예측 타깃

**화면:** 시장정보, 현재 스트레스, 미래 정답의 관계.

| 미국 모델의 데이터 | 금융적 의미 |
| --- | --- |
| SPY | 주식시장 수익률과 하락·변동성 정보 |
| VIX | 옵션시장에 반영된 변동성 정보 |
| Baa 회사채 수익률 − 10년 국채 수익률 | 장기 이력을 가진 신용 스트레스 대용지표 |

신용 변수를 ICE BofA High Yield OAS로 부르지 않는다.

**발언 초안**

주식·변동성·신용 채널을 결합해 현재 스트레스 지수인 MSI를 계산했습니다. MSI가 그 시점 이전의 과거 분포에서 90분위 기준 이상이면 관측 Stress Event로 정의합니다. 모델의 정답은 다음 1거래일부터 10거래일 사이에 이 사건이 한 번이라도 나타나는지입니다.

이 타깃은 이미 스트레스가 진행 중인 관측도 포함할 수 있다. 새로운 위기의 시작을 항상 10일 전에 예측한다는 설명은 사용하지 않는다.

### 3장. 검증 설계

**화면:** 과거 학습, 경계의 10개 관측 제외, 이후 테스트를 보여주는 기간 그림.

**발언 초안**

금융 시계열의 순서를 유지하기 위해 expanding walk-forward 검증을 사용했습니다. 10일 정답은 미래 관측을 포함하므로 테스트 시작 직전의 학습 관측 10개를 제외해 정답 구간의 중첩을 막았습니다. 과거 차트의 점수는 각 테스트 구간에서 생성한 OOS 예측입니다.

미래 정답을 만드는 것과 미래정보를 입력변수에 넣는 것은 구분한다. 이 검증 설계만으로 원자료의 당시 발표 지연이나 개정 이력까지 검증했다고 주장하지 않는다.

### 4장. 성능과 운영모델 선택

**화면:** 미국 10일 OOS 성능표. 동일 표에 평가기간과 기준 임계값을 표시한다.

| 기준 README의 지표 | Logistic | XGBoost |
| --- | ---: | ---: |
| ROC-AUC | 0.9220 | 0.8991 |
| PR-AUC | 0.8065 | 0.7778 |
| Precision | 0.4932 | 0.5929 |
| Recall | 0.8665 | 0.7760 |
| False Alarm Rate | 0.1885 | 0.1128 |

출처: [기준 커밋 README의 10-Day Horizon 표](https://github.com/tina77302/market-stress-early-warning/blob/8d3e75f55d68dacea36925de409553f13157cbb2/README.md). 고정 0.5 임계값, OOS 5,060개 관측, 양성비율 17.47%로 기재된 결과다. 이번 문서화에서 재산출하지 않았으며 최종 발표 전 평가기간을 원본 산출물과 대조한다.

**발언 초안**

Logistic은 AUC와 Recall이 높아 사건 탐지 측면에서 강점을 보였습니다. XGBoost는 기준 임계값에서 Precision이 높고 False Alarm Rate가 낮았습니다. 경보를 확인해야 하는 운영 부담까지 고려해 기존 XGBoost 배포 구조를 유지합니다.

False Alarm Rate는 실제 음성 중 양성 경보의 비율이다. 경보 중 오경보의 비율인 1−Precision과 구별한다. Risk Score 70은 실제 사건 확률 70%로 해석하지 않는다.

### 5장. 대시보드 시연

**화면:** 실제 동작이 확인된 기능과 데이터 기준일.

**발언 초안**

먼저 점수의 관측일을 확인하고 현재 Risk Score와 MSI를 읽습니다. SHAP으로 현재 배포 모델의 점수를 높이거나 낮춘 변수를 살펴본 뒤, 과거 OOS 차트와 검증 화면으로 이동합니다. 현재 출력의 설명과 과거 테스트 예측을 구분해 확인하도록 구성했습니다.

SHAP을 사건 확률의 퍼센트포인트 변화나 인과관계로 설명하지 않는다. 별도 Z-score WATCH를 메인 제품 경보로 시연하지 않는다.

### 6장. WATCH 연구 종료와 10월 사례

**화면:** 한국 D3 비교표, 제품 미채택 결정, 사례 해석 한 문장.

| 한국 D3의 5일 선행 커버리지 | Z-score WATCH | XGBoost |
| --- | ---: | ---: |
| 사전 경고가 있었던 사례 / 전체 사례 | 6 / 19 (31.6%) | 8 / 19 (42.1%) |

**발언 초안**

WATCH는 미래정보 누수 없이 구현됐다는 연구 판정을 받았고 MSI 기반 사건에서는 좋아 보였습니다. 그러나 실제 급락 D3로 평가했을 때 추가 효용을 충분히 입증하지 못했습니다. 한국 19개 사례 중 5일 선행 커버리지는 WATCH 6개, XGBoost 8개였고 WATCH 연속 ON 구간 대부분은 5일 내 급락으로 이어지지 않았습니다. 이 결과를 근거로 연구를 종료하고 제품에 추가하지 않기로 결정했습니다.

10월 사례에서도 12일 첫 급락 때는 OFF였고 13일 급락 당일 ON이었습니다. 15일 추가 급락 전에 ON이었다는 범위에서만 설명할 수 있습니다. 당시 실제 발행 기록이 없으므로 이 사례는 retrospective shadow result입니다.

이 수치와 판정은 프로젝트 책임자가 2026-10-19 확정한 연구 결과다. D3 상세 정의·대상 지수·평가기간·에피소드 규칙 및 원본 결과는 [결정 문서의 근거 범위](../decisions/zscore-watch-research-closeout-2026-10-19.md#3-연구-결론과-근거)에 따라 최종 발표 자료에 연결한다. 19개 사례만으로 통계적 유의성이나 일반적 우열을 주장하지 않는다.

### 7장. Live Monitoring Log와 Data Health

**화면:** 실제 신호 생성 시점에 고정 저장할 필드.

| 필수 항목 | 발표에서 설명할 의미 |
| --- | --- |
| `generated_at` | 실제 생성 시각 |
| `observation_date` | 사용한 시장 관측일 |
| `risk_score` | 당시 XGBoost 위험 점수 |
| `msi` | 당시 현재 스트레스 수준 |
| `model_hash` | 실제 사용 모델의 식별값 |
| `input_hash` | 실제 사용 입력의 식별값 |
| `data_freshness` | 소스별 관측일·가용시각·지연·채움 여부 |

**발언 초안**

과거 데이터를 다시 계산한 결과만으로는 그날 시스템이 실제로 알고 있던 정보와 발행한 신호를 증명하기 어렵습니다. 앞으로는 매일 실제 생성 시점에 입력과 모델, 점수, 데이터 신선도를 고정 저장하겠습니다. 정답 관측기간이 끝난 뒤 이 기록을 평가하면 실전 OOS 검증의 근거가 됩니다.

실제 게시·전송 여부는 `published_at`과 전달 상태로 별도 기록한다. 해시뿐 아니라 모델 산출물과 입력 스냅샷도 보관한다. LIVE·SHADOW·BACKFILL을 구분하며 기존 기록을 덮어쓰지 않는다.

Data Health는 데이터의 FRESH·STALE·MISSING·UNKNOWN 상태를 보여준다. 서버가 정상 응답하는지와 데이터가 최신인지는 구분한다. 로그의 구축 자체와 검증된 실전 예측 성능도 구분한다.

현재 확인되지 않은 운영 기능이나 배포 상태를 완료로 표시하지 않는다. 상세 수용 기준은 [제품 완성 계획](../operations/project-completion-plan.md)을 사용한다.

| 0:50~1:20 | 과거 OOS 차트 | 사전에 고른 사례와 테스트 예측 구분 |
| 1:20~2:00 | 모델 검증 | Logistic·XGBoost의 경보 적중률과 탐지율 차이 |

Log·Data Health는 실제 구현과 QA를 마친 경우 7장에서 짧게 시연한다. 미완료 상태에서는 설계·계획 화면으로 제시한다.

시연용 캡처는 코드·모델·데이터 기준일을 맞춰 준비한다. 네트워크 문제 시 캡처로 전환하고 캡처 시점을 밝힌다. 발표 중 재학습이나 원자료 수집을 실행하지 않는다.

## 6. 예상 질문과 짧은 답변

| 질문 | 답변 요지 |
| --- | --- |
| VIX만 보는 것보다 나은가? | 주식·신용 채널을 함께 사용하는 설계다. VIX 단독 대비 우위는 동일 조건의 비교 결과가 있을 때만 주장한다. |
| 왜 10거래일인가? | 단기 리스크 점검의 기준 기간으로 정했다. 1·5·20일 결과는 보완 자료이며 모든 목적에 최적인 기간이라고 주장하지 않는다. |
| Logistic의 AUC가 더 높은데 왜 XGBoost인가? | 기준 임계값에서 탐지율과 오경보 부담이 다르다. 운영 목적과 경보 적중률을 함께 보고 기존 선택을 유지한다. |
| 점수 70은 확률 70%인가? | 보정된 사건 발생 확률이 아니다. 모델 기반 위험 신호로 해석한다. |
| Stress Event와 D3는 같은가? | MSI 기준 사건과 별도 실제 급락 기준으로 정의가 다르다. 평가 결과를 구분한다. |
| WATCH 실험은 실패인가? | 정상 구현한 후보도 실제 급락 기준에서 추가 효용을 입증하지 못할 수 있다. 이번에는 연구 근거를 남기고 미채택을 결정했다. |
| WATCH가 10월 급락을 사전에 잡았나? | 첫 급락 때 OFF였고 13일 급락 당일 ON이었다. 당시 발행 기록이 없어 사후 shadow 결과로만 설명한다. |
| Z-score를 모두 제거했나? | 별도 WATCH 경보 연구를 종료했다. 기존 MSI 표준화와 모델 입력변수 사용은 유지한다. |
| Log가 있으면 실전 성능 검증이 끝나나? | 생성 시점의 증거가 쌓이기 시작한다. 충분한 미래 정답이 성숙한 뒤 사전에 정한 기준으로 평가한다. |
| 실제로 경고했다는 것을 어떻게 증명하나? | 계산 기록과 실제 게시·전송 기록을 분리하고 각 시각과 상태를 보관한다. |
| 지금 어디까지 완성됐나? | 시연 직전 확인한 구현·배포·QA 증거에 따라 답한다. 예정 기능은 계획으로 명시한다. |

## 7. 부록의 10월 사례 표

| 날짜 | 제공된 일간 수익률 | Z-score WATCH | 해석 |
| --- | ---: | --- | --- |
| 2026-10-12 | -3.79% | OFF | 첫 급락의 WATCH 선행 탐지를 주장할 수 없음 |
| 2026-10-13 | -6.25% | ON | 급락 당일 ON. 당일 하락 이전 발행을 입증하지 않음 |
| 2026-10-14 | -0.56% | ON | 스트레스 발생 이후 ON 유지 |
| 2026-10-15 | -8.13% | ON | 앞선 관측일에도 ON이었던 추가 급락 사례 |

당시 실제 WATCH 발행 로그는 없다. 표 제목과 설명에 **retrospective shadow result**를 표시한다. 대상 지수와 수익률 산식은 원본 연구 자료에 대조하며 임의로 보충하지 않는다.

추가 부록에는 MSI·타깃 수식, 1·5·10·20일 OOS 표, 시장별 평가 차이, SHAP·LOFO의 범위, D3 원본 정의, Log의 실제 QA 결과를 둔다.

## 8. 발표 준비 작업과 완료 기준

1. **근거 고정:** 발표 코드·모델·데이터 기준일과 평가기간을 기록한다. 기존 OOS 표와 D3 원본 결과를 대조한다.
2. **자료 제작:** 본문 8장에 각각 하나의 핵심 메시지와 직접 연결되는 근거를 배치한다.
3. **시연 준비:** 2분 동선을 확인하고 같은 기준일의 캡처를 확보한다. 구현 예정 기능은 계획으로 표시한다.
4. **발언 연습:** 본문과 시연을 합쳐 10분으로 리허설한다. 세부 수식과 긴 지표 설명은 부록으로 넘긴다.
5. **질의응답 준비:** 표의 질문에 20~30초 안에 답하고 필요한 원본 근거를 바로 찾을 수 있게 한다.

완료 기준은 연구 결론, 발표 수치, 제품 화면과 구현 상태가 서로 일치하는 것이다. 새 모델·WATCH 튜닝은 발표 준비 범위에 추가하지 않는다.
