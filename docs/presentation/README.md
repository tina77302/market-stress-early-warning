- 기준일: 2026-10-19 (Asia/Seoul)
- 발표 가정: **10분 발표 + 5분 질의응답**. 실제 배정 시간이 확인되면 조정한다.
- 현재 상태: **발표 기획 문서. 운영 기능 구현·AWS 배포·QA 완료를 의미하지 않는다.**
- 기준 코드: `8d3e75f55d68dacea36925de409553f13157cbb2`
- 필수 연결: [연구 종료 결정](../decisions/zscore-watch-research-closeout-2026-10-19.md), [제품 완성 계획](../operations/project-completion-plan.md)

## 1. 발표의 핵심 메시지

시장·변동성·신용 정보를 결합해 향후 10거래일 스트레스 위험을 평가하고, 시간 순서를 보존한 OOS 검증을 수행했다. 추가한 WATCH 연구는 실제 급락 기준의 추가 효용을 충분히 입증하지 못해 제품화하지 않기로 결정했다. 이제 실제 생성 시점의 신호를 보존하여 실전 검증이 가능한 제품으로 완성한다.

청중이 기억할 내용은 다음과 같다.

- 현재 스트레스 MSI, 미래 위험 Risk Score, 관측 Stress Event의 역할이 다르다.
- 모델 선택은 탐지율과 오경보의 운영상 차이를 함께 보고 판단한다.
- 사후 재계산과 당시 실제 발행한 신호를 구분한다.
- 연구 결과를 근거로 기능 추가를 중단하고 완성 범위를 고정했다.

## 3. 슬라이드별 발언 요지

### 1장: 연구 질문

현재 관측 가능한 주식·변동성·신용시장 정보로 향후 10거래일 안에 프로젝트가 정의한 시장 스트레스 사건이 나타날 위험을 평가했습니다. 사용자는 점수와 원인을 함께 확인하여 추가 리스크 점검에 활용할 수 있습니다.

### 2장: 데이터와 사건 정의

미국 모델은 SPY, VIX, Moody's Baa 회사채 수익률에서 10년 국채 수익률을 뺀 신용 스트레스 대용지표를 사용합니다. 신용 변수를 HY OAS로 부르지 않습니다. MSI는 현재 스트레스를 측정하며 과거 분포의 90분위 기준 이상이면 관측 Stress Event로 정의합니다.

기존 MSI 계산과 일부 입력변수의 Z-score는 유지합니다. 이번에 종료한 것은 별도 Z-score WATCH 경보 연구입니다.

### 3장: 타깃과 검증

10일 타깃은 다음 1~10거래일 중 사건이 한 번이라도 나타나는지입니다. 시간 순서를 보존한 expanding walk-forward를 사용하고 학습 라벨의 미래 구간이 테스트 시작과 겹치지 않도록 10개 관측을 제외합니다.

미래 데이터는 학습 정답 구성에 사용하며, 입력변수에 섞는 것과 구분합니다. 코드상의 purge가 당시 원자료의 발표 지연·개정 이력까지 검증했다는 의미는 아닙니다.

### 4장: 성능과 모델 선택

현재 README의 미국 10일 OOS 결과에서 Logistic은 AUC와 Recall이 높았고 XGBoost는 기준 임계값에서 Precision이 높고 False Alarm Rate가 낮았습니다. 기존 배포 모델은 XGBoost를 유지합니다.

| README 기재 지표 | Logistic | XGBoost |
| --- | ---: | ---: |
| ROC-AUC | 0.9220 | 0.8991 |
| PR-AUC | 0.8065 | 0.7778 |
| Precision | 0.4932 | 0.5929 |
| Recall | 0.8665 | 0.7760 |
| False Alarm Rate | 0.1885 | 0.1128 |

출처는 [기준 커밋 README](https://github.com/tina77302/market-stress-early-warning/blob/8d3e75f55d68dacea36925de409553f13157cbb2/README.md)의 10-Day Horizon 표다. 고정 0.5 기준이며 이번 문서 작업에서 재산출하지 않았다. 한국 D3 비교표의 성능과 다른 평가다. 최종 발표에는 평가기간·관측수·양성비율을 동일 원본과 대조해 함께 표기한다.

### 5장: WATCH 연구의 결론

WATCH는 미래정보 누수 없이 구현됐다는 연구 판정을 받았지만, 실제 급락 D3 기준에서는 추가 효용을 충분히 입증하지 못했습니다. 한국 D3 5일 선행 커버리지는 WATCH 6/19, XGBoost 8/19였고 WATCH 연속 ON 구간 대부분은 5일 내 급락으로 이어지지 않았습니다.

따라서 제품 메인 경보에는 추가하지 않고 연구를 종료합니다. 결과가 기대와 달라도 그 근거를 남기고 제품 범위를 결정한 점이 연구 성과입니다.

수치와 판정의 출처는 프로젝트 책임자가 2026-10-19 확정한 연구 결과입니다. 세부 정의와 재현 범위는 [결정 문서](../decisions/zscore-watch-research-closeout-2026-10-19.md#3-연구-결론과-근거)에 기록합니다.

### 6장: 10월 사례의 정확한 해석

| 날짜 | 제공된 일간 수익률 | WATCH |
| --- | ---: | --- |
| 2026-10-12 | -3.79% | OFF |
| 2026-10-13 | -6.25% | ON |
| 2026-10-14 | -0.56% | ON |
| 2026-10-15 | -8.13% | ON |

첫 급락은 놓쳤고 13일에는 이미 급락한 당일 ON이었습니다. 15일 추가 급락 전에도 ON이었지만 당시 실제 발행 기록은 없습니다. 따라서 이 결과는 retrospective shadow result로 설명합니다.

이 한계를 해결하려면 앞으로 실제 생성 시점의 입력·모델·점수·신선도를 고정 저장해야 합니다.

### 7장: 제품 시연

현재 화면에서는 기존 XGBoost Risk Score, MSI, 과거 OOS 추이와 SHAP 설명을 확인합니다. 데이터 기준일을 먼저 보여주고 점수와 주요 기여변수를 설명합니다.

Live Monitoring Log와 Data Health는 실제 구현·QA를 완료한 경우에만 완성 기능으로 시연합니다. 그 전에는 계획으로 표시합니다. 별도 Z-score WATCH를 메인 경보로 보여주지 않습니다.

### 8장: 마무리

이제 Live Monitoring Log, Data Health, 최종 UI, AWS 호환버전 배포, 전체 QA, 발표 정리 순서로 완료합니다. 앞으로 쌓이는 실제 기록을 정답 관측기간 종료 후 평가하여 실전 OOS 성능을 확인하겠습니다.

로그가 있다는 사실만으로 예측 성능을 입증했다고 말하지 않습니다.

| 경과 | 시연 | 설명할 내용 |

## 5. 질의응답 준비

| 질문 | 답변 요지 |
| --- | --- |
| VIX만 봐도 되지 않나? | 주가와 신용 채널까지 결합하는 설계다. VIX 단독 대비 우위는 동일 조건 비교 결과가 있을 때만 주장한다. |
| 왜 10거래일인가? | 단기 리스크 점검의 기준 horizon으로 두었다. 1·5·20일 검증은 보완 자료이며 10일이 모든 목적에 최적이라는 주장은 하지 않는다. |
| Logistic AUC가 더 높은데 왜 XGBoost인가? | 고정 기준에서 XGBoost의 경보 적중률·오경보 부담이 달랐다. 기존 운영 선택을 유지하며 우월성을 일반화하지 않는다. |
| 점수 70은 사건 확률 70%인가? | 보정된 확률이 아니다. 모델 기반 위험 신호로 해석한다. |
| Stress Event와 D3는 같은 정답인가? | 다르다. Stress Event는 MSI 기준, D3는 별도 실제 급락 연구 기준이다. 결과를 섞지 않는다. |
| WATCH 실험은 실패인가? | 구현과 제품 채택은 다른 판단이다. 실제 급락 기준의 추가 효용을 입증하지 못했다는 결론을 남겼다. |
| WATCH가 10월 급락을 미리 잡았나? | 첫 급락 때 OFF였고 13일 급락 당일 ON이었다. 당시 발행 기록도 없어 사후 shadow 결과로만 설명한다. |
| Z-score를 전부 없앴나? | 별도 WATCH 경보 연구를 종료했다. 기존 MSI 표준화와 입력변수 사용은 유지한다. |
| 지금 실시간 자동 경보 서비스가 완성됐나? | 실제 완료한 범위로 답한다. 로그·신선도·운영 배포·QA가 남아 있으면 남은 작업이라고 명시한다. |
| Log를 만들면 실전 성능 검증이 끝나나? | 실제 시점의 증거가 쌓이기 시작한다. 충분한 미래 정답이 성숙한 뒤 고정된 기준으로 평가해야 한다. |
| 기록은 실제로 사용자에게 경고했다는 증거인가? | 생성 로그와 게시·전송 기록을 구분한다. 실제 게시·전송 시각과 상태가 있어야 전달까지 설명할 수 있다. |

## 6. 최종 발표 전 준비 순서

1. 코드·모델·데이터 기준일과 발표 수치를 고정한다.
2. D3 원본 연구 정의와 결과 표를 기존 산출물에서 연결한다. 새 튜닝을 시작하지 않는다.
3. 10월 사례의 관측일·대상 지수·수익률 산식과 shadow 표기를 원본에 대조한다.
4. 실제 구현 완료 범위만 캡처하고 예정 기능에는 계획 표시를 남긴다.
5. 본문 8장과 시연을 합쳐 10분 리허설을 수행한다.
6. 예상 질문은 20~30초 답변을 준비하고 상세 수식·지표·추가 실험은 부록에 둔다.

### 부록 후보

- MSI·타깃·입력변수의 상세 정의와 기준 코드
- 1·5·10·20일 OOS 성능과 임계값
- 미국·한국의 데이터·평가기간·모형 차이
- SHAP와 LOFO의 해석 범위
- D3 원본 정의·에피소드 산출 규칙·평가 표
- Live Monitoring Log 데이터 계약과 실제 QA 결과

본문에서 신호 개선 연구를 다시 제안하지 않는다. 최종 발표 자료에는 원본 근거가 있는 수치와 확인한 구현 상태만 사용한다.
