# 김주미 담당 발표: WATCH 검토·운영 보완·모의투자

- 기준일: 2026-10-19 (Asia/Seoul)
- 발표 순서: 팀원의 전체 시스템 발표 다음, 본문 6~9장
- 시간 가정: **4분**. 전체 발표는 팀원 6분 + 김주미 4분의 10분 예시다.
- 관련 문서: [전체 발표 기획](README.md), [연구 종료 결정](../decisions/zscore-watch-research-closeout-2026-10-19.md), [제품 완성 계획](../operations/project-completion-plan.md)
- 모의투자 규칙·화면·성과 원본은 현재 미확인이다. 원본을 대조하기 전에는 설계·검증 질문으로 설명한다.

## 1. 담당 범위와 발표의 중심 질문

팀원이 전체 시스템의 구조·성능을 설명한 뒤, 다음 질문을 맡는다.

> 추가 경보를 제품에 넣을 근거가 충분한가? 실제 운영에서 신호를 검증하려면 무엇이 필요한가? 그 신호를 모의투자에 활용했을 때는 무엇을 확인해야 하는가?

모델 수식·데이터 전체·OOS 성능표를 다시 길게 설명하지 않는다. 기존 XGBoost Risk Score를 기준으로 연구 판단, 기록 보완, 활용 검증을 이어서 설명한다.

## 2. 발표 시작과 인계

팀원이 마지막 시연 후 다음과 같이 인계한다.

> 이어서 김주미 님이 추가 경보 검토에서 확인한 한계와 운영 검증 보완 방향, 모의투자 영역을 설명하겠습니다.

김주미 시작 발언:

> 앞서 설명한 기존 시스템을 기준으로, 추가 경보를 검토한 결과와 실제 운영에서 보완할 부분, 모의투자에서 확인할 내용을 말씀드리겠습니다.

발표 담당을 실제 구현·연구 기여 전체로 확대해 설명하지 않는다.

## 3. 6장: WATCH 추가 검토와 제품 미채택 판단

- 시간: 1:00
- 화면: 한국 D3 커버리지 비교표, 10월 사례 요약, 제품 미채택 결정
- 핵심: 구현이 정상이어도 실제 급락 기준의 추가 효용이 충분해야 제품에 채택한다.

| 한국 D3 5일 선행 커버리지 | Z-score WATCH | XGBoost |
| --- | ---: | ---: |
| 사전 경고 사례 / 전체 사례 | 6 / 19 (31.6%) | 8 / 19 (42.1%) |

### 발언 초안

WATCH는 미래정보 누수 없이 구현됐다는 연구 판정을 받았고 MSI 기반 사건에서는 좋아 보였습니다. 그러나 실제 급락 D3 기준으로 확인했을 때 추가 효용을 충분히 입증하지 못했습니다. 한국 19개 사례의 5일 선행 커버리지는 WATCH가 6개, 기존 XGBoost가 8개였습니다. WATCH 연속 ON 구간 대부분도 5일 내 급락으로 이어지지 않았습니다.

10월 사례에서도 12일 첫 급락 때는 OFF였고 13일에는 급락 당일 ON이었습니다. 15일 추가 급락 전에도 ON이었다는 범위로만 해석할 수 있습니다. 당시 실제 발행 기록이 없으므로 사후 재계산한 shadow 결과입니다. 이 근거로 별도 WATCH는 제품에 추가하지 않고 연구를 종료했습니다.

### 근거와 해석 범위

수치와 구현 판정은 프로젝트 책임자가 2026-10-19 제공·확정한 연구 결론이다. 이번 문서화에서 재현하거나 새 튜닝하지 않았다. 19개 사례만으로 통계적 유의성이나 모든 시장의 우열을 주장하지 않는다.

Stress Event는 기존 MSI 기준 사건, D3는 별도 실제 급락 기준이다. WATCH 연속 구간의 적중 여부와 일별 False Alarm Rate도 분모가 달라 구분한다.

기존 XGBoost 경보 구간의 WATCH 명칭은 유지한다. 기존 MSI·입력변수의 Z-score 사용도 유지하며 별도 Z-score WATCH 연구만 종료한다.

## 4. 7장: 운영 검증에서 보완할 부분

- 시간: 0:45
- 화면: 필수 로그 7개 필드. 긴 기술 설명은 부록
- 핵심: 당시 실제로 생성한 신호와 사후 재계산 결과를 구분할 증거가 필요하다.

| 항목 | 저장할 내용 |
| --- | --- |
| `generated_at` | 실제 생성 시각 |
| `observation_date` | 사용한 시장 관측일 |
| `risk_score` | 당시 XGBoost 위험 점수 |
| `msi` | 당시 시장 스트레스 수준 |
| `model_hash` | 실제 사용 모델 식별값 |
| `input_hash` | 실제 사용 입력 식별값 |
| `data_freshness` | 소스별 시점·지연·채움·품질 상태 |

### 발언 초안

이번 검토에서 드러난 중요한 공백은 그날 실제로 생성한 신호와 과거 데이터를 다시 계산한 결과를 구분할 기록이 부족하다는 점입니다. 그래서 생성 시각, 관측일, 점수와 MSI, 모델·입력 식별값, 데이터 신선도를 고정 저장하는 Live Monitoring Log를 우선합니다.

실제 게시 여부도 따로 남기고 Data Health로 지연과 결측을 보여줍니다. 그 뒤 미래 정답이 쌓이면 당시 생성한 기록을 대상으로 실전 OOS 성능을 평가할 수 있습니다.

### 자세한 질문을 받으면

해시와 함께 입력 스냅샷·모델 산출물을 보관한다. LIVE·SHADOW·BACKFILL을 구분하며 과거 행을 덮어쓰지 않는다. 생성 기록과 게시·전송 기록을 분리한다. 10거래일 정답이 성숙하기 전의 행을 음성으로 처리하지 않는다.

이 기능의 구현·QA가 미완료라면 발언은 보완 계획으로 유지한다. 로그 구축 자체를 실전 성능 검증 완료라고 설명하지 않는다.

## 5. 8장: 모의투자 영역

- 시간: 1:45
- 화면: 실제 구현이 확인되면 해당 화면·규칙표·비교 성과. 미확인 또는 미구현이면 검증 설계 표
- 핵심: 기존 신호의 예측력과 투자 적용 효과는 별도로 검증한다.

### 발표가 답해야 할 질문

**같은 대상과 기간에서 기존 위험 신호를 활용하면 비용과 상승장 기회비용까지 포함해 수익·낙폭·위험노출이 어떻게 달라지는가?**

비교 기준으로 동일 자산의 매수보유를 검토할 수 있다. 이는 설계 제안이며 기존 구현에서 이미 사용했다고 가정하지 않는다. 점수에 따른 현금 비중 조절·매매 규칙도 원본 확인 전에는 특정 숫자나 실행 규칙을 확정하지 않는다.

### 현재 근거 범위에서 사용할 발언 초안

모의투자 영역에서는 위험 점수를 투자 판단에 연결했을 때의 효과를 별도로 검토합니다. 앞서 본 예측 성능이 높다는 사실만으로 투자성과가 좋다고 말할 수는 없습니다. 위험을 피하는 과정에서 거래비용이 늘거나 상승 기회를 놓칠 수 있기 때문입니다.

먼저 어떤 자산을 어떤 기간에 대상으로 했고 점수가 어떤 투자 판단에 연결되는지 명확히 해야 합니다. 신호가 실제로 알려진 뒤 실행 가능한 가격으로 거래했는지, 수수료와 슬리피지를 어떻게 반영했는지도 중요합니다.

비교에서는 같은 대상과 기간의 단순 기준전략을 두고 비용 차감 수익률과 최대낙폭, 회전율과 위험노출을 함께 보겠습니다. 과거 자료로 다시 계산한 결과는 백테스트로 구분하고, 실제 시점의 모의투자는 당시 신호와 모의 주문·체결·잔고를 시간순으로 남겨야 합니다. 기존 모델은 유지하면서 투자 적용 효과를 확인하는 것이 이 영역의 목적입니다.

이 초안은 검증 목적과 확인 기준을 설명한다. 미확인 수익률·최대낙폭·전략 우위나 실제 구현 완료를 주장하지 않는다.

### 실제 구현 원본을 확인한 뒤 채울 발표 정보

| 확인 항목 | 필요한 원본 | 현재 상태 |
| --- | --- | --- |
| 구현 유형 | 화면·코드·실행 기록. 과거 백테스트 또는 실제 시점 모의투자 | 미확인 |
| 대상·기간·초기자금 | 실험 설정과 데이터 기준일 | 미확인 |
| 투자 규칙 | 점수에서 보유·비중·매매로 연결되는 실제 규칙 | 미확인 |
| 신호·체결 시점 | 신호 가용시각, 주문·체결 시각과 가격 정의 | 미확인 |
| 기준전략 | 동일 자산·기간·초기조건의 비교 설정 | 미확인 |
| 비용 | 수수료·세금·스프레드·슬리피지 가정 | 미확인 |
| 성과 | 비용 차감 수익률·최대낙폭·회전율·노출의 원본 산출 | 미확인 |
| 실전 기록 | 신호·주문·체결·잔고·현금 이력 | 미확인 |

이미 구현한 범위가 확인되면 그 사실과 결과로 발언을 교체한다. 그렇지 않으면 슬라이드 제목을 **「모의투자 적용 설계와 검증 계획」**으로 쓴다.

과거 OOS 점수에 적용한 투자 규칙을 같은 평가기간의 수익률을 보며 최적화했다면 그 성과를 독립적인 투자전략 OOS 결과라고 주장하지 않는다. 모델 연구를 다시 시작하거나 발표 직전 성과가 좋아지는 규칙을 탐색하지 않는다.

## 6. 9장: 마무리와 남은 작업

- 시간: 0:30
- 화면: 기존 제품 완성 순서

### 발언 초안

추가 모델 연구는 여기서 멈추고 기존 XGBoost 경보 구조를 유지합니다. 앞으로 Live Monitoring Log, Data Health, 최종 UI, AWS 호환버전 배포, 전체 QA, 발표 정리 순서로 완성합니다. 경보를 실제 시점의 기록으로 평가하고 모의투자에서도 비용과 위험을 함께 살피는 것이 남은 방향입니다.

모의투자 설명을 새 기능 구축 전체의 지시로 확대하지 않는다. 현재 구현 범위와 계획을 구분한다.

## 7. 김주미 담당 예상 질문

| 질문 | 20~30초 답변 요지 |
| --- | --- |
| WATCH 연구는 실패인가? | 정상 구현한 후보도 제품 채택을 위한 추가 효용이 부족할 수 있다. 실제 급락 기준에서 근거를 남기고 미채택을 결정했다. |
| 10월 급락을 사전에 잡았나? | 첫 급락은 OFF였고 13일 급락 당일 ON이었다. 당시 발행 기록이 없으므로 retrospective shadow result다. |
| WATCH를 없애면 기존 모델도 바뀌나? | 별도 Z-score WATCH만 미채택이다. 기존 XGBoost 경보와 MSI·입력변수는 유지한다. |
| Log가 있으면 예측력이 좋아지나? | 직접적인 성능 개선을 보장하지 않는다. 당시 실제 신호를 평가할 증거가 생긴다. |
| 모의투자에서 수익이 났나? | 확인한 원본 성과가 있을 때만 수치로 답한다. 미확인 상태에서는 결과 제시를 보류한다. |
| 왜 수익률만 비교하지 않나? | 위험 회피로 낙폭이 줄어도 수익 기회를 놓치거나 거래비용이 늘 수 있어 함께 평가한다. |
| 당일 점수로 당일 종가에 거래했나? | 실제 신호 가용시각과 체결 가정을 확인해 답한다. 종가 이후 알려진 정보로 같은 종가 체결을 가정하지 않는다. |
| 과거 OOS 점수면 투자전략도 OOS인가? | 투자 규칙을 같은 구간의 성과를 보고 정했다면 독립 평가가 아니다. 신호와 투자 규칙의 평가를 나누어 본다. |
| 백테스트와 실제 모의투자의 차이는? | 과거 자료 재생과 당시 실제 신호에 따른 주문·체결 기록의 차이다. 실거래 수익으로도 표현하지 않는다. |

데이터·학습·Walk-forward 세부 질문은 팀원의 원본 설명과 연결하고, 구현 담당이 확인한 근거를 사용한다.
