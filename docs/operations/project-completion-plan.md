# 제품 완성 및 Live Monitoring 실행 계획

- 확정일: 2026-10-19 (Asia/Seoul)
- 상태: **실행 계획 + 2026-10-19 WIP 코드 점검 + 2026-10-20 배포 사이트 모의투자 점검 반영. 체크리스트는 운영·배포 완료를 의미하지 않는다.**
- 기준 결정: [Z-score WATCH 연구 종료](../decisions/zscore-watch-research-closeout-2026-10-19.md)
- 발표 연결: [발표 준비](../presentation/README.md)

## 1. 범위와 완료 순서

제품은 기존 XGBoost Risk Score, 현재 스트레스 MSI, 관측 Stress Event 구조를 유지한다. 별도 Z-score WATCH 통합과 새 모델 연구는 이번 범위에 포함하지 않는다.

| 순서 | 작업 | 확인 상태 | 완료에 필요한 증거 |
| --- | --- | --- | --- |
| 1 | Live Monitoring Log | WIP의 불변 로그·조회 코드 확인, 운영 완료 미확인 | 실제 운영 행·입력/모델 재현·지속 저장 |
| 2 | Data Health | WIP 코드·기존 수동 갱신 보고 확인, 현재 운영 미확인 | 실제 소스별 상태·화면·실패/지연 확인 |
| 3 | 최종 UI 확인 | WIP 기존 로컬 QA 보고 있음, 발표 버전 확인 필요 | Risk Score·MSI·Stress Event 및 시점의 일관성 |
| 4 | AWS 호환버전 배포 | 배포 사이트 응답 확인. 모의투자는 WIP 최신이 아닌 이전 버전으로 동작, 정확한 배포 커밋 미확인 | 고정 버전 배포와 실행·재시작·저장 확인 |
| 5 | 전체 QA | 2026-10-20 배포 사이트 모의투자 기능 점검 완료(결함 P2·P3). 나머지 최종 버전 QA 필요 | 데이터 수집부터 로그·화면까지 검증 기록 |
| 6 | 발표 정리 | 담당·대본·코드 근거 보완, 리허설/원본 확정 필요 | 동일 기준 버전의 발표·시연·수치 |

상태는 담당자가 실제 증거를 확인한 후 변경한다. 새 연구를 시작하여 완료 범위를 늘리지 않는다.

### 코드 점검의 적용 범위

원격 `wip/data-automation`의 `4a75acd1e1e73e58c9cb600519401a9ca4a22bc1`에서 운영·모의투자 코드를 확인했다. 현재 발표 문서 브랜치에 이 구현을 병합하거나 배포하지 않았다. [발표 근거 점검](../presentation/implementation-evidence.md)에 고정 소스와 남은 확인을 기록했다. 이번에는 WIP 실행·QA를 재수행하지 않았으므로 기존 보고를 이번 테스트 결과로 표시하지 않는다.

아래 데이터 계약은 목표다. 실제 구현에서는 `generated_at`이 게시 시각이고 `model_inference_at`이 추론 시각이다. `input_snapshot_sha256`은 게시 payload 해시이므로 아래 `input_hash`의 feature row 계약과 동일하다고 간주하지 않는다. 기록 유형은 LIVE/RETROSPECTIVE이고 Data Health 상태는 CURRENT/DELAYED/STALE/PARTIAL/ERROR다. 아래 SHADOW/BACKFILL과 FRESH 등의 개념 구분을 실제 enum 이름으로 설명하지 않는다.

모의투자는 WIP의 수동 주문·비용·환전·통합 계정 평가 기능을 확인했다. 2026-10-20 배포 사이트를 테스트 계정으로 점검한 결과, 배포판은 시장별 독립 계좌(USD 100,000·KRW 100,000,000)와 무비용 종가 체결로 동작했다. WIP 비용·통합 계정은 배포되지 않은 것으로 보인다. 발표 전에 WIP를 배포할지 팀이 정하고, 배포 버전을 기록한다. 점검에서 찾은 만료 거절 주문 복원 오류(P2)와 금액 줄바꿈(P3)은 제품 QA에서 수정한다. 다일 수익률·MDD·비교전략 원본은 미확인이다. 기능 설명과 성과 입증을 분리하고 발표 수치를 만들기 위한 규칙 탐색은 진행하지 않는다.

## 2. Live Monitoring Log의 목적

매일 실제 신호 생성 시점에 다음 질문에 답할 수 있는 기록을 고정 저장한다.

> 그날 그 시각 시스템은 어떤 데이터를 알고 있었고, 어떤 모델과 규칙으로 어떤 위험 신호를 생성했는가?

과거 데이터를 다시 계산한 결과를 당시 실제 기록처럼 소급 작성하지 않는다. 계산 기록과 사용자에게 실제 게시·전송한 기록도 구분한다.

### 필수 저장 필드

아래는 구현할 데이터 계약이다. 예시 설계이며 현재 저장된 로그 형식이라는 뜻이 아니다.

| 필드 | 의미와 저장 규칙 |
| --- | --- |
| `generated_at` | 실제 계산 완료 시각. UTC ISO 8601과 시간대 정보 저장, 화면은 KST 변환 가능 |
| `observation_date` | 사용한 시장 관측일. 생성 시각과 별도이며 시장 달력을 함께 해석 |
| `risk_score` | 기존 XGBoost 출력과 동일한 점수. 스케일·반올림 규칙 명시 |
| `msi` | 해당 관측일의 현재 시장 스트레스 지수 |
| `model_hash` | 실제 사용한 모델 산출물 바이트의 SHA-256 |
| `input_hash` | 실제 추론 입력의 컬럼 순서·자료형·값·시점을 고정 직렬화한 SHA-256 |
| `data_freshness` | 소스별 관측일·가용/수집 시각·지연·채움 여부·품질 상태 |

### 함께 저장할 맥락

| 필드 또는 정보 | 필요한 이유 |
| --- | --- |
| `run_id`, `market`, `record_type` | 실행과 시장 구분. `LIVE`, `SHADOW`, `BACKFILL` 구별 |
| `status`, `error_reason` | 정상·계산 실패·자료 부족을 구분. 실패를 LOW로 기록하지 않음 |
| `raw_model_output`, `risk_level`, `rule_version` | 표시 점수·기존 경보 등급·적용 임계값의 추적 |
| `stress_event`, `stress_threshold`, `msi_version` | 현재 관측 사건과 당시 적용한 과거 분포 기준 보존 |
| `code_commit`, `config_hash`, `feature_schema_version` | 코드·설정·특징 정의 변경 추적 |
| `model_training_cutoff`, `model_registered_at` | 미래에 학습한 모델로 과거 LIVE 기록을 만들지 않았는지 확인 |
| `source_available_at`, `fetched_at` | 관측일이 같아도 당시 실제 입수 가능했던 자료인지 확인 |
| `published_at`, `delivery_status` | 실제 게시·전송했을 때 기록. 생성만 했다면 null 또는 미게시 상태 |
| 입력 스냅샷·모델 manifest 위치 | 해시가 가리키는 입력과 모델을 실제로 재현할 수 있게 보관 |

모델·입력 해시만 보관하고 원본 산출물과 입력 스냅샷을 버리면 재현할 수 없다. 재현에 필요한 산출물을 지속 저장소에 함께 보관하며 비밀키는 기록하거나 커밋하지 않는다.

### 저장 원칙

- 기록은 append-only로 저장하고 기존 행을 수정하거나 덮어쓰지 않는다.
- 네트워크 재시도로 같은 실행이 중복 저장되지 않도록 `run_id + market` 등 고유키와 멱등성을 둔다.
- 같은 관측일의 정정·재계산은 새 실행으로 저장하고 이전 실행과 연결한다.
- 과거일 재계산은 실제 실행 시각과 `BACKFILL` 또는 `SHADOW` 유형을 남긴다. `generated_at`을 과거로 바꾸지 않는다.
- 거래일 기준 매일 생성한다. 휴장일 작업을 수행하면 휴장 상태와 마지막 관측일을 표시한다.
- 실패·결측·지연도 남긴다. 마지막 정상값을 사용할 때 원래 날짜와 대체 사용 사실을 함께 표시한다.
- 재시작·재배포·컨테이너 교체 후에도 로그와 증거 산출물이 유지되어야 한다.
- 미래 Stress Event·D3 정답은 별도 outcome 테이블에 평가 규칙 버전 및 판정 시각과 함께 추가한다. 원래 신호 행을 바꾸지 않는다.

### Prospective OOS 평가 규칙

1. 운영 시작 시점의 모델, 임계값, 평가기준과 변경 정책을 기록한다.
2. LIVE 신호는 생성 당시 실제 가용한 입력과 그 전에 등록된 모델만 사용한다.
3. 10거래일 타깃은 해당 미래 관측기간이 끝난 뒤 평가한다. 아직 정답을 모르는 행을 0으로 취급하지 않는다.
4. 기존 Stress Event 타깃과 D3 보조 평가는 정의·분모·기간을 분리한다.
5. LIVE, SHADOW, BACKFILL 결과를 섞어 실시간 성능으로 발표하지 않는다.
6. 모델을 변경하면 버전을 나누어 비교한다. 과거 로그를 새 모델 결과로 교체하지 않는다.
7. 로그 시작 자체와 검증된 실전 성능을 구분한다. 경보일 적중률, 누락, 선행일, 경보 지속성은 충분한 정답이 쌓인 후 평가한다.

### 완료 기준

- [ ] 실제 실행으로 필수 7개 필드와 버전 맥락을 가진 LIVE 로그가 생성된다.
- [ ] 원본 입력·모델 산출물로 해시 일치와 동일 점수 재현을 확인한다.
- [ ] 재시도·동일 관측일 재계산·백필·실패가 구분되고 원래 행이 유지된다.
- [ ] 서버 재시작 후에도 이전 로그를 조회할 수 있다.
- [ ] 계산과 실제 게시 여부를 구분해 조회할 수 있다.

## 3. Data Health 표시

소스별 관측일, 실제 입수 시각, 계산 시각과 시장 달력을 바탕으로 신선도를 표시한다. 모든 소스에 단순한 24시간 기준을 일괄 적용하지 않는다. 휴장, 소스별 발표 지연, 시간대 차이를 고려한다.

| 상태 | 표시 의미 |
| --- | --- |
| FRESH | 해당 소스의 기대 갱신주기와 가용시점에 부합 |
| STALE | 기대 시점이 지났는데 최신 가용 관측을 반영하지 못함 |
| MISSING | 필요한 입력 또는 결과가 없음 |
| UNKNOWN | 신선도를 판단할 메타데이터가 부족함 |

최종 신호 상태는 필수 소스의 건강 상태와 연결한다. API가 HTTP 200을 반환하거나 서버 health가 정상이라는 사실을 데이터 최신성으로 표시하지 않는다.

- [ ] Risk Score 기준일과 소스별 관측일을 함께 확인할 수 있다.
- [ ] 결측·지연 시 경고가 보이고 LOW 또는 정상 OFF와 구별된다.
- [ ] 이전 값 대체와 forward fill 여부를 노출한다.
- [ ] 한국·미국의 휴장, 발표 지연, API 부분 실패를 확인한다.

## 4. 최종 UI 확인

- [ ] 메인 경보는 기존 XGBoost Risk Score와 기존 등급 기준을 사용한다.
- [ ] 별도 Z-score WATCH 경보·배지·결합 규칙을 메인에 추가하지 않는다.
- [ ] MSI, Risk Score, Stress Event의 역할과 기준일을 구별한다.
- [ ] Risk Score를 보정된 사건 발생 확률로 표시하지 않는다.
- [ ] 최신 점수와 과거 walk-forward OOS 차트를 구분한다.
- [ ] LIVE 로그와 사후 SHADOW 결과의 유형·시점을 표시한다.
- [ ] Live Monitoring Log·Data Health가 미구현이면 계획 상태로 표시한다.
- [ ] 미국·한국 시장과 SHAP·차트의 부분 실패 상태를 확인한다.

## 5. AWS 호환버전 배포

현재 문서는 특정 AWS 서비스나 배포 성공을 가정하지 않는다. 선택한 환경의 실제 실행 결과를 기록한다.

- [ ] 배포할 Git 커밋, 모델 해시, 설정 버전을 고정한다.
- [ ] Python·Node·모델 직렬화 라이브러리 버전과 서버 CPU 아키텍처 호환성을 확인한다.
- [ ] 경로·환경변수·API 주소·CORS·포트·시간대 설정을 해당 환경에서 확인한다.
- [ ] 비밀키는 저장소 밖에서 주입하고 로그에 출력하지 않는다.
- [ ] 로그·입력 스냅샷·모델을 임시 컨테이너 파일시스템 밖에 지속 저장한다.
- [ ] 배치 스케줄·동시 실행 방지·재시도·실패 기록을 확인한다.
- [ ] health, 최신 데이터, Data Health, 로그 조회를 각각 확인한다.
- [ ] 재시작과 롤백 후 모델·로그·화면의 일관성을 확인한다.

## 6. 전체 QA와 완료 판정

| 영역 | 핵심 확인 | 보관할 증거 |
| --- | --- | --- |
| 데이터 | 관측일·입수시각·결측·지연·휴장 처리 | 소스별 상태와 입력 스냅샷 |

| 시점 | 생성 시각 이전 가용 정보, 미래 정답 미혼입 | 모델 manifest와 가용시각 |
| API·UI | 점수·MSI·사건·기준일·경보 등급 일치 | API 응답과 화면 캡처 |

| 배포 | AWS 실행·재시작·롤백 | 배포 커밋과 실행 기록 |
| 발표 | 수치 출처·연구 종료·실시간/사후 구분 | 발표 문서와 기준 산출물 |

QA에서 발견한 제품 결함은 수정하되 모델 연구를 재개하지 않는다. 체크리스트를 통과한 범위만 구현 완료로 발표한다.
